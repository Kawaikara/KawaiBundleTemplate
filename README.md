# Kawai Bundle Template

This repository is a GitHub Template for a Kawaikara `.kawai` Bundle. The
example opens Google with one TypeScript Provider and contributes three
PluginView panels: one from the Provider and two from its Provider-scoped
Plugin. Kawaikara shows a browser-like panel bar only because more than one
panel exists; a single contribution fills the area without that bar.

```bash
pnpm install
pnpm typecheck
pnpm build
```

The finished archive is written to `release/*.kawai`. A `.kawai` file is a ZIP
container, but Kawaikara accepts only the application-specific extension.

## Develop inside Kawaikara

This template includes `kawaikara.dev.json`, so no separate development server
or manual `.kawai` installation is required.

1. Open Kawaikara Preferences and select **Developer**.
2. Enable **Bundle development mode** and save the preference.
3. Select **Add project** and choose this repository directory.
4. Keep **Hot reload** enabled. Kawaikara watches `src`, builds an immutable
   local revision, validates its manifests and permissions, and replaces the
   running Bundle after each change.

Kawaikara owns the development build and stores generated JavaScript, source
maps, and immutable revisions under this project's
`.kawaikara/development/` directory. Git ignores that directory, and detaching
the project removes it. Kawaikara app data keeps only the attached-project
registry.

Change the project-local output directory through `package.json` when needed:

```json
{
  "kawaikara": {
    "development": {
      "outputDirectory": ".kawaikara/development"
    }
  }
}
```

The output must remain inside the project and cannot overlap `src` or a watched
directory. Detach and reattach the project after changing it, and add a custom
location to `.gitignore` when it is not already covered.

## JSON completion

The checked-in `.vscode/settings.json` automatically associates the generated
schemas in `.kawaikara/schemas/` with `package.json`, `kawaikara.dev.json`, and
every Bundle, Provider, and Plugin manifest. `pnpm install` and
`pnpm schemas:sync` refresh that directory from the installed
`@kawaikara/site-api`, so updating the API dependency updates completion and
validation at the same time without changing tracked files.

The checked-in `schemas/` directory is only a fallback for Site API releases
that predate packaged schemas. Once the installed dependency provides them,
the synchronizer always prefers the package copy. VS Code therefore provides
field completion, enum suggestions, hover documentation, and validation
without an extension.

To debug Provider or Plugin code, enable the Main process debugger in the same
preference page, save, and start the included VS Code configuration named
**Attach to Kawaikara Bundle**. Its default loopback port is `9230`; update
`.vscode/launch.json` if you select another port in Kawaikara. Source maps are
generated by the app-owned development builder, so breakpoints stay attached
when a new revision is hot reloaded.

Development Bundles execute trusted local code in Kawaikara's Main process.
Only attach projects whose code and dependencies you trust.

## API dependency

Bundle projects import `@kawaikara/site-api`, but the package is not currently
published to the npm registry. This template pins the prebuilt package attached
to the immutable `v1.0.0` GitHub Release in `Kawaikara/kawai-site-api`. A fresh clone can therefore
run `pnpm install` without a sibling Kawaikara checkout, a local `link:` path,
or a build of the desktop monorepo.

Kawaikara releases the API independently of the desktop app. A matching
`vX.Y.Z` tag in [`Kawaikara/kawai-site-api`](https://github.com/Kawaikara/kawai-site-api)
builds the package and publishes a tested `.tgz` on that dedicated repository's
GitHub Releases page. The Git tag identifies the immutable API source and the
release artifact is the installable package. Keep the Bundle
manifest's `apiVersion` compatible with the selected Site API release.

When developing both repositories locally, you may temporarily replace the Git
dependency with an absolute `link:` path to `packages/site-api`. Do not commit
that machine-specific path.

## Plugin scope

The included Plugin lives below its Provider and therefore attaches only to
that Provider. Bundle-level Plugins can target one or many Providers through
`providerIds`. Plugin-only and App-attached Bundles are intentionally not part
of Site API v1; an App Plugin needs a separate, narrower App context and
permission model before it can be enabled safely.

Panel titles are presentation text and may repeat. Kawaikara selects a panel by
the stable combination of its Provider or Plugin owner id and local panel id.
HTML panels run in a sandboxed document without Kawaikara IPC or access to the
overlay document.

Site-specific Inject code belongs beside its Provider. The app supplies only
generic primitives such as viewer lifecycle, settings, shortcuts, sessions,
and unified PiP. Keep translated Provider presentation text in the neighboring
`locale.json`, reference it with `contributes.locale.resource`, and keep DOM
selectors and PiP page policy in `@provider()` rather than `manifest.json`. Use
`defineProviderLocale()` when targeting the next Site API release so message
ids are checked by TypeScript and runtime injection strings use the same
fallback rules as preference labels. This template keeps direct JSON access
until that API release is published.
